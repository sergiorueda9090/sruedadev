Antes de entrar a AWS
01

Sube los cambios locales a GitHub

En tu computador, antes de tocar AWS

Crear y preparar el servidor en AWS
02

Crea la instancia EC2

Consola de AWS → EC2 → Instancias

En la consola de AWS, busca EC2 → Launch Instance. Completa así:

  1. Nombre: sruedadev-prod.
  2. Imagen (AMI): Ubuntu Server (LTS), la que diga "Free tier eligible".
  3. Tipo de instancia: t2.micro o t3.micro (lo que diga "Free tier eligible" en tu región).
  4. Par de claves: Create new key pair → nómbralo sruedadev-key, tipo RSA, formato .pem. Descárgalo, es la única vez que lo entregan.
  5. Network settings → Edit: crea un Security Group con las tres reglas de la tabla.
TipoPuertoOrigenPara qué
SSH22My IP (recomendado)Conectarte por terminal
HTTP800.0.0.0/0Tráfico web normal
HTTPS4430.0.0.0/0Tráfico cifrado (SSL)

Almacenamiento: 8-20 GB gp3 está bien dentro de la capa gratuita. Luego Launch Instance y espera a Running.

Atención

No pierdas el archivo .pem: es la única llave para entrar por SSH.

03

Asigna una IP elástica (Elastic IP)

Consola de AWS → EC2 → Elastic IPs

La IP pública por defecto cambia si reinicias la instancia. Necesitas una fija para el dominio.

  1. Network & Security → Elastic IPs → Allocate Elastic IP address → Allocate.
  2. Selecciona la IP → Actions → Associate Elastic IP address.
  3. Elige sruedadev-prod → Associate.

Anota esa IP — la llamamos TU_IP_ELASTICA en el resto de la guía.

04

Terminal de tu computador

Error común

Si da UNPROTECTED PRIVATE KEY FILE: chmod 400 "ruta\a\sruedadev-key.pem" y reintenta. Cuando pregunte por el fingerprint, escribe yes.

06

Clona el repositorio

Por SSH, dentro de la instancia
Servidor — SSH
cd ~
git clone https://github.com/sergiorueda9090/sruedadev.git
cd sruedadev
git config core.fileMode false

El proyecto queda en /home/ubuntu/sruedadev.

Corrección

git config core.fileMode false evita un problema real que apareció al desplegar: cuando más adelante (Paso 10) se cambian permisos de archivos para que Apache pueda escribir la base de datos, git detecta ese cambio de permisos como si fuera una modificación de contenido — y git status termina mostrando todos los archivos del repositorio como "modified" sin que hayas tocado nada, bloqueando futuros git pull. Este comando le dice a git que ignore los permisos del archivo y solo mire el contenido real.

Si el repositorio es privado

GitHub pedirá usuario y un Personal Access Token como contraseña (Settings → Developer settings → Personal access tokens), no tu contraseña normal.

07

Crea el entorno virtual e instala las dependencias

Por SSH, dentro de ~/sruedadev
Servidor — SSH
python3 -m venv env
source env/bin/activate
pip install --upgrade pip
pip install -r requirements.txt

Verás (env) al inicio del prompt mientras esté activo.

Corrección

requirements.txt fija Django==5.2.18 (LTS), no Django 4.0. Algunas imágenes recientes de Ubuntu traen python3 apuntando a una versión muy nueva de Python (3.13+), que eliminó el módulo cgi — Django 4.0 todavía lo necesitaba internamente y fallaba con ModuleNotFoundError: No module named 'cgi' al correr migrate. Django 5.2 ya no depende de ese módulo. Mientras uses el requirements.txt del repositorio tal cual, no deberías ver ese error.

10

Da los permisos correctos a la carpeta del proyecto

Por SSH — puedes salir del entorno virtual con deactivate

Apache corre como www-data. Como la base de datos es SQLite, www-data necesita poder escribir en la carpeta raíz del proyecto (SQLite crea archivos temporales junto a db.sqlite3) y en el propio archivo.

Servidor — SSH
sudo usermod -aG www-data ubuntu
sudo chown -R ubuntu:www-data /home/ubuntu/sruedadev
sudo chmod 775 /home/ubuntu/sruedadev
sudo chmod 664 /home/ubuntu/sruedadev/db.sqlite3
sudo chmod o+x /home/ubuntu
Corrección

Antes este paso usaba chmod -R 775 (recursivo, sobre todo el proyecto). Eso cambia el permiso de cada archivo tracked por git y, aunque ya corriste git config core.fileMode false en el Paso 6, es innecesario: solo la carpeta raíz necesita ser escribible, para que SQLite pueda crear su archivo de journal junto a db.sqlite3. El resto de archivos (plantillas, CSS, imágenes) no necesitan cambiar de permiso.

El paso que más se olvida

Por defecto, Ubuntu crea /home/ubuntu con permisos 750: solo el usuario ubuntu puede entrar ahí, sin importar los permisos de sruedadev por dentro. Apache (como www-data) necesita permiso de búsqueda (+x) en cada carpeta del camino. Sin el chmod o+x /home/ubuntu de arriba, Apache responde 403 Forbidden con Permission denied... search permissions are missing on a component of the path en el log de errores, aunque todo lo demás esté bien.

Nota

Si usermod no surte efecto en tu sesión actual, cierra la conexión SSH (exit) y vuelve a entrar. Los chmod sí aplican de inmediato.

11

Configura Apache con mod_wsgi

Por SSH

Crea el archivo de configuración del sitio:

Servidor — SSH
sudo nano /etc/apache2/sites-available/sruedadev.conf

Pega este contenido completo:

/etc/apache2/sites-available/sruedadev.conf
Contenido del archivo
WSGIDaemonProcess sruedadev python-home=/home/ubuntu/sruedadev/env python-path=/home/ubuntu/sruedadev
WSGIProcessGroup sruedadev

<VirtualHost *:80>
    ServerName sruedadev.com
    ServerAlias www.sruedadev.com

    Alias /static/ /home/ubuntu/sruedadev/staticfiles/
    <Directory /home/ubuntu/sruedadev/staticfiles>
        Require all granted
    </Directory>

    <Directory /home/ubuntu/sruedadev/srueda>
        <Files wsgi.py>
            Require all granted
        </Files>
    </Directory>

    WSGIScriptAlias / /home/ubuntu/sruedadev/srueda/wsgi.py

    ErrorLog ${APACHE_LOG_DIR}/sruedadev-error.log
    CustomLog ${APACHE_LOG_DIR}/sruedadev-access.log combined
</VirtualHost>
Corrección — importante

WSGIDaemonProcess y WSGIProcessGroup van antes del bloque <VirtualHost>, no dentro. En la primera versión de esta guía estaban dentro del bloque :80, y al instalar el certificado SSL en el Paso 15, Certbot clona todo lo que hay dentro del VirtualHost hacia un nuevo bloque :443 — duplicando WSGIDaemonProcess sruedadev y rompiendo Apache con Name duplicates previous WSGI daemon definition. Declarándolo una sola vez, fuera del bloque, Certbot nunca lo copia y el Paso 15 funciona sin fricción.

Guarda y activa el sitio:

Servidor — SSH
sudo a2dissite 000-default.conf
sudo a2ensite sruedadev.conf
sudo apache2ctl configtest
sudo systemctl restart apache2

apache2ctl configtest debe responder Syntax OK.

13

Apunta sruedadev.com a la IP elástica en Route 53

Consola de AWS → Route 53 → Hosted zones

Abre la zona sruedadev.com.

Registro raíz: Create record → Record name vacío → Type A → Value: tu IP elástica → Create records.

Registro www: Create record → Record name www → Type A → misma IP → Create records.

Propagación

Puede tardar minutos a un par de horas en propagar del todo.

15

Instala el certificado SSL gratuito (HTTPS)

Por SSH — solo después de que el Paso 14 funcione
Servidor — SSH
sudo apt install -y certbot python3-certbot-apache
sudo certbot --apache -d sruedadev.com -d www.sruedadev.com

Da un correo, acepta términos, y cuando pregunte por redirigir HTTP a HTTPS, elige redirigir.

Servidor — SSH
sudo apache2ctl configtest
sudo systemctl restart apache2

Abre https://sruedadev.com y confirma el candado.

Renovación automática
Servidor — SSH
sudo certbot renew --dry-run
Si aparece "Name duplicates previous WSGI daemon definition"

Significa que WSGIDaemonProcess quedó dentro del bloque <VirtualHost> (revisa el Paso 11). Edita /etc/apache2/sites-available/sruedadev-le-ssl.conf si ya tiene contenido y borra ahí la línea duplicada, o reescribe sruedadev.conf con WSGIDaemonProcess fuera del bloque como en el Paso 11 y vuelve a correr certbot --apache.

Si algo falla

Diagnóstico por síntoma, con los errores que ya aparecieron en este despliegue
SíntomaCausaQué hacer
ModuleNotFoundError: No module named 'cgi' al correr migrate Python del servidor es 3.13+ (eliminó el módulo cgi) y Django está en una versión vieja que aún lo usa Confirma que requirements.txt tiene Django==5.2.18 (o superior) y vuelve a pip install -r requirements.txt.
403 Forbidden / Permission denied ... search permissions are missing on a component of the path Falta permiso de búsqueda en /home/ubuntu (se crea en 750 por defecto) sudo chmod o+x /home/ubuntu (Paso 10).
git pull dice "local changes would be overwritten" y git status muestra todos los archivos como modified Un chmod -R previo cambió el modo de cada archivo y git lo interpreta como contenido modificado git config core.fileMode false (Paso 6), luego git status debe quedar limpio y git pull funciona normal.
Certbot: Error while running apache2ctl configtest / Name duplicates previous WSGI daemon definition WSGIDaemonProcess está dentro del <VirtualHost :80> y Certbot lo duplicó al clonar el bloque hacia :443 Mueve WSGIDaemonProcess y WSGIProcessGroup fuera del bloque VirtualHost, a nivel de archivo (Paso 11), luego sudo apache2ctl configtest && sudo systemctl restart apache2 y vuelve a correr certbot --apache.
El HTML carga pero sin estilos No corriste collectstatic, o la ruta Alias /static/ no coincide Repite el Paso 9 y confirma que staticfiles/ existe en ~/sruedadev.
DisallowedHost at / El dominio o la IP no están en ALLOWED_HOSTS Edita .env (Paso 8) y agrega el host que falta, separado por coma, sin espacios.
El sitio carga por IP pero no por dominio DNS aún no propagó Espera y confirma con nslookup sruedadev.com.

Para cualquier cambio en sruedadev.conf, siempre corre sudo apache2ctl configtest antes de reiniciar.
